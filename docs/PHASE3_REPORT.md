## 1. 기준 프로젝트 분석 요약

## 2. 구현 내용 (A → B → C → D)

### A. 직접 조작하는 제조
- 같은 게임 행동 `PLACE_INGREDIENT`(솥에 놓기 = 계량 문제 열기, 아직 투입 아님)를 세 방식이 공유: ① 재료 클릭 → 솥 클릭 ② 드래그 → 솥에 드롭(포인터 이벤트, 마우스·터치 공통) ③ 키보드(Enter 집기, Tab, Enter 놓기, Esc 취소). 솥 밖에 놓으면 선반으로 돌아감(흔들림 표시).
- 계량 패널이 열린 동안 다른 재료 잠금, 확정·투입한 재료는 다시 놓을 수 없음, 투입 중복 방지(리듀서 가드).
- 상태: 재료 과제 `pending → measured(답 확정) → done(투입)`, 주문 `stirProgress 0~100`, `brewing → bottled(품질·보상 확정) → paid`. 화면 연출이 아니라 이 상태로 진행을 판단.
- 젓기: 솥 안에서 막대를 움직인 **거리**를 솥 너비 기준으로 누적(솥 너비 약 2배 이동이면 완료, 프레임 수·기기 성능 무관). ‘🌀 젓기’ 버튼은 한 번에 25. 한 번 전송 최대 25로 제한, 완료 후 무시. 진행에 따라 액체 색이 레시피 색으로 바뀌고 반짝임·소용돌이가 늘어남.
- 새로고침 복구: 패널 열림·입력 중 답·확정 결과·투입·젓기 진행·병 담기 후·판매 후. 붓기·병 담기·덧문 연출은 재생하지 않고 최종 모습.
- UI 정리: 가운데 솥 + 아래 재료 선반, 왼쪽 접는 ‘주문 메모·레시피북’(탭), 오른쪽 계량 패널(평소엔 ‘만드는 순서’ 안내). 세로 태블릿(≤900px)에서는 세로로 쌓고 계량 패널은 아래에서 올라오는 판. 버튼 높이 48px 이상, 색만이 아니라 글로 상태 표시.

### B. 오답으로도 이어지는 제조
- 유효한 숫자 답(또는 비교 선택)을 내면 그 재료의 결과를 확정(재입력 없음). 형식 오류는 안내만 하고 확정·오답 집계 없음.
- 정답: ✓와 입력값·필요한 양, ‘풀이 보기’, ‘이 양으로 투입하기’.
- 오답: 입력값 빨간색 + ‘입력한 양 · 필요한 양과 달라요’ 문구, 입력한 양/필요한 양 칸 구분, 키패드 자리에 **실제 문제의 계산 과정**(조건 → 식 → 자연수 계산 → 소수점 처리 → 단위와 결과, 1보다 작은 배수면 작아지는 이유 포함). 소수점 위치·덧셈 실수는 원인이 분명할 때만 한 줄 덧붙임. ‘이 양으로 투입하기’ → 입력한 양 그대로 투입(자동 투입 없음, 정답으로 바꾸지 않음).
- 아주 큰·작은 값도 기록은 그대로, 솥 그림은 액체 높이 고정·라벨 길이 제한으로 깨지지 않음.
- 품질: 두 재료 정확 → 만족 100%, 하나 → 조금 아쉬움 80%, 둘 다 다름 → 불만족 60%. `Math.floor(정상 × 퍼센트 / 100)` 정수 연산. 힌트·‘네?’ 무관. 병에 담을 때 품질·보상·손님 반응 확정 저장 → 전달 때 1회 지급.
- 손님은 포션 빛깔에 반응(“오늘은 별빛이 정말 선명하네요!” 등), 학생을 탓하지 않음. 병 그림도 품질에 따라 흐려짐.

### C. 다양한 주문과 ‘네?’
- 주문 4유형, 레시피 4종(별빛·용기·새싹·안개), 손님 4종(여우 코코·토끼 보리·고양이 나비·늑대 달이 — 같은 그림 틀에 색·귀 모양만 바꾼 임시 그래픽).
- 대사(원래 말)와 쉬운 설명, 주문 메모를 주문 생성 때 만들어 저장(재현 가능). ‘네?’는 `askCount`만 올림 — 숫자·조건·보상 불변, 쉬운 설명은 무엇을 계산할지 말하지만 정답은 말하지 않음(테스트로 전체 후보 검사). 제조대 주문 메모에서 원래 말·쉬운 설명 다시 보기.
- 생활 소재 특별 주문(하루 최대 1건): 초콜릿 14.35g×10(허용 예외), 작은 돌, 유리구슬, 리본, 줄넘기 줄, 연필. “계산한 숫자를 마법 재료량으로 쓴다(단위 변환 아님)” 규칙을 메모·쉬운 설명·해설에 표시. 손님 지정 재료는 레시피보다 우선, 다른 재료는 ‘레시피 기본량 그대로’ 지정량 과제.
- 비교 주문(⑦): 기준 식과 바뀐 식, 10배/같음/1/10배 선택 → 해설 → 목표량 자동 계량(학습 연출). 품질은 선택 정오로.
- 하루 구성: 새 유형은 그날 꼭 등장, 생활 소재·비교·복습 각 최대 1건, 첫 손님은 일반 주문, 일반 주문 2건 이상. 후보는 목록으로 만든 뒤 덱에서 뽑음(무한 재시도 없음), 연속한 여러 병 주문의 병 수는 같지 않게.
- 정상 판매금: 여러 병 5 × 병 수, 그 밖의 주문 20. 마감 화면에서 여러 병 판매 병 수와 맞춤·특별 주문 제조 건수를 구분.

### D. 유형 자동 소개, 학습 기록, 복습
- 소개 단계(`day.introStage`, 일차와 별개): 첫 영업 ①② → ③④ → ⑤⑥ → ⑦. 영업 완료마다 1단계, 정답률·힌트와 무관. 그날 처음 나오는 유형은 영업 시작 때 소개 카드(설명·예시), 확인 후 주문 받기.
- 데이터 검증(테스트): 모든 단계에서 소개된 유형마다 출제 후보 존재, 레시피 기본량·배수·생활 소재 인수가 범위 안(예외 제외), 레시피 `supports`가 실제 기본량과 일치.
- 문제 기록(`problemLog`): 유효한 답 1회 = 기록 1개(문제 ID 중복 방지). 조건·인수·목표값·학생 입력·정오·힌트 단계·해설 확인·일반/복습·주문 유형·과제 종류(계산/지정량/비교). 지정량 과제는 계산 정답률에서 제외.
- 주문 결과(`orderLog`): 만족도·정상 판매금·실제 지급액.
- 복습(`review`): 오답 → 후보, 다음 영업부터 같은 유형·다른 인수(0.5/0.50 같은 표기 차이는 같은 수로 비교), 하루 최대 1건, 정답이면 해결, 오답이면 유지하되 바로 다음 날은 쉬기, 알맞은 후보가 없으면 일반 주문. 원래 문제와 복습 문제 ID 관계 저장.
- 학습 기록 화면(타이틀 → 📒): 요약(유형별·영업별), 문제 기록(완료·미완료), 복습, 손님 반응, 이전 기록.
- 학습 결과 JSON 버전 2: 유형별 집계, 문제 기록, 복습 후보, 주문 결과, 영업별 집계, 이전 기록. 개인 식별 정보 없음(손님 이름도 넣지 않음).

### 발견·수정한 문제
1. 투입 연출(1.1초) 동안 재료 선반이 잠겨 빠르게 다음 재료를 끌면 조용히 무시됨 → 연출은 화면 효과로만 두고 병에 담는 동안만 잠금.

## 5. 검증 결과

### 실행 환경의 제한 (중요)
이 작업 환경은 조직 정책으로 npm 저장소(registry.npmjs.org) 접근이 차단되어 있습니다(HTTP 403, 이번에도 확인). 그래서 아래는 **실행하지 못했습니다.**

| 미실행 | 대신 한 것 |
|---|---|
| `npm ci` / `npm install` | — |
| 실제 **Vite production build** (`npm run build`) | 이 환경에 있던 React 19.2 + esbuild 0.27로 같은 소스를 `base=/MoonlightPotionShop-5-2-4/`로 번들 (Vite 빌드가 아님) |
| 실제 `@types/react`를 쓴 TypeScript 검사 | TypeScript 6.0 strict(`noUnusedLocals` 등 프로젝트 tsconfig 그대로). 게임 로직·데이터·저장 코드는 실제 타입으로 완전 검사, 화면(TSX) 코드는 간이 React 타입 정의로 검사 |
| `package-lock.json` 생성 | 만들지 않음(조작하지 않음). workflow는 lock 파일이 있으면 `npm ci`, 없으면 `npm install` |
